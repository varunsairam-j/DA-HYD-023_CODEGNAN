File Management System :
----------------------------------
* Software provided by the operating system for creating, storing, retrieving, updating, and deleting files.
* Operations are done manually or through application code.

--> Key Functions of FMS:
----------------------------------
* File Creation & Deletion --> Create a File, Delete a File
* File Access & Retrieval --> Read Data, Data  --> Sequential access, Direct access, Indexed access.
* File Organization --> Sequential files, Indexed files, Hashed files
* File Manipulation --> Insert, update, delete, or append data inside files.
* File Sharing and Protection --> The system can control permissions such as: Read, Write, Execute
* Backup & Recovery --> You can make copies of files and restore them after a failure.

--> Drawbacks of FMS:
-------------------------------
* Data Redundancy --> Unnecessary duplication of data.
* Data Inconsistency --> If one file is updated but another copy is not, data becomes inconsistent.
* Poor Data Security --> Security is only at file-level.
* Limited Data Sharing --> Multiple users accessing the same file at the same time may cause conflicts.
* No Data Relationships --> like Primary key & Foreign key.
* Difficult Backup & Recovery --> Recovery after failure is hard.
* Lack of Query Language --> Every operation needs custom program logic.
* Scalability Issues --> Managing huge datasets using ordinary files becomes increasingly difficult and inefficient.

 (TCL) :
-----------
Transaction Control Language 
Transaction = A group of SQL operations.
* We may perform several SQL operations, and then decide whether to permanently save them or undo them.

=> BEGIN --> Start Transaction

COMMIT --> Save Changes Permanently.
ROLL --> Undo the Operation.
SAVEPOINT --> Acts as a Checkpoint.

--> ROLLBACK can undo uncommitted transaction changes, but it does not undo changes that have already been committed

ACID Properties :
-----------------------
A = ATOMICITY --> Atomicity means a transaction is treated as one complete unit.
--> Either the whole transaction happens, or the transaction does not happen.

C = CONSISTENCY --> Consistency means that a transaction should take the database from one valid state to another valid state.
--> Consistency ensures that the transaction doesn't leave the database in an invalid state.

I = ISOLATION --> Transactions should not improperly interfere with each other.
--> When multiple transactions happen concurrently, 
one transaction should not improperly interfere with or see the unfinished/intermediate work of another transaction.

D = DURABILITY --> Durability = Once committed, the change stays.
--> Once a transaction has been successfully committed, 
its changes should remain saved, even if something like a system failure happens afterward.

Normalization :
---------------------
Organizing data into multiple related tables.
Instead of storing everything together, we separate the information.

Data Redundancy --> The same piece of information is unnecessarily stored multiple times.
Redundancy = unnecessary repeated data.

3 common anomalies that can happen because of poorly organized/redundant data: 
--> Insertion = Cannot insert some information without having unrelated information.
--> Update = Same information is stored in multiple rows, so changing it requires changing multiple places.
--> Deletion = Deleting one piece of information accidentally causes us to lose other useful information.

Normalization Rules :
----------------------------
Normal forms are rules that tables should satisfy to reduce redundancy and prevent data anomalies.

=> 1 NF = Each cell should contain a single, atomic value — not a list or multiple values.
One cell → One value

COMPOSITE Key :
------------------------
A Composite Key is a key made up of two or more columns together that uniquely identifies a row.
--> PRIMARY KEY (student_id, course_id)

Functional Dependency :
--------------------------------
Partial Dependency = If a non-key column depends on only part of a Composite Key, it is called Partial Dependency.
Transitive dependency = If a non-key attribute should not depend on another non-key attribute.
2NF removes Partial Dependency.
3NF removes Transitive Dependency.

=> 2 NF = Every non-key attribute must depend on the entire Composite Key, not just a part of it.
--> If a table doesn't satisfy 2NF because it has a partial dependency, 
	   we decompose (split) the table into related tables so that the partial dependency is removed.

=> 3 NF = Remove attributes that depend on another non-key attribute.

Normalization = Organizing data so each piece of information is stored in the appropriate place, 
								reducing unnecessary repetition and preventing anomalies.

CANDIDATE Key :

A Candidate Key is an attribute or a combination of attributes that can uniquely identify each row in a table.
Candidate Keys = possible choices for Primary Key
Primary Key = the Candidate Key we actually choose

CTE : Common Table Expression
------------------------------------------
First prepare a result → give that result a name → use the named result in your main query.

A normal CTE is not a permanently stored table. It exists only for the SQL statement in which you define it.

CTE = a named intermediate result that I can use while executing this particular SQL statement.

Syntax :
------------
WITH cte_name AS (
-- Query that produces the result
)

SELECT *
FROM cte_name;


Recursive CTE --> The CTE refers to itself.
They're useful when data has a repeating or hierarchical relationship.

--> Anchor Member => Anchor query → gives the starting row
--> Recursive Member => Recursive query → uses the previous result to generate the next rows
--> Stop => Stopping condition → eventually produces no more rows

WITH RECURSIVE cte_name AS (

    -- 1. START
    anchor_query

    UNION ALL

    -- 2. REPEAT
    recursive_query
)
SELECT *
FROM cte_name;
